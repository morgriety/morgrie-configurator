# MORGRIE Configurator｜强制 Git 与发布流程

## 适用范围与规则入口

本流程适用于本项目所有后续开发、版本更新、公开源码同步及正式发布。根目录 [AGENTS.md](../AGENTS.md) 是 Codex 新任务的入口：开始工作前必须读取本文件；制定测试计划、执行验收或整理结果前必须同时读取 [TESTING_RULES.md](TESTING_RULES.md)。现有开发规范、UI 设计要求、设备操作安全、许可证和问题台账规则保持有效。

本文件规定操作顺序和批准边界；[BUILDING.md](../BUILDING.md) 规定当前构建及公开导出方法。脚本存在、测试通过、历史用户反馈或自动化触发配置都不构成当前 Commit、Merge、Push 或部署授权。有冲突或规则缺失时，先报告并停止受影响步骤，不自行改写规则优先级。

历史准备副本与历史验收记录继续保留，但不能替代本流程的内部 main 冻结、版本对应核查及用户批准。本流程本身不触发分支切换、提交、合并、同步、上传或部署。

## 五阶段流程与验收条件

### 01｜开发阶段

**执行范围**

- 新功能、Bug 修复及 UI 修改原则上在 feature 分支进行；不得直接在内部 main 上开展日常功能开发。若任务从 main 开始，先在任务授权范围内准备 feature 分支，不直接修改 main 的业务代码。
- 开始前核对分支、HEAD、工作区及任务范围。发现其他未提交修改时先报告并保留，不覆盖、重置或擅自混入本任务。
- 所有应用改动在内部开发仓库完成。公开源码目录和公开仓库是发布镜像，不是第二个功能开发场所。
- 每次修改后先进行与变更相匹配的验证，整理实际修改、结果、未覆盖事项及风险，再准备可审阅的 Commit 内容。文档改动可使用内容、引用及差异检查；不得把未执行的构建或实机测试写成通过。

**进入下一阶段的条件**：开发工作完成，必要软件测试通过，明确仍待用户验收的项目与已知问题；若要执行 Commit，必须已有用户对该次提交范围的明确批准。提交完成本身不代表功能验收或合并批准。

### 02｜功能验收完成

**合并前检查**

1. 核对 feature 和内部 main 的实际 HEAD、Git 工作区、待合并差异，确认没有夹带未验收或无关功能。
2. 核对必要测试和相应用户验收记录，区分软件验证、实机验证、未测试和已知限制。遵守 TESTING_RULES.md，不重复要求已完成且无回归需要的测试，不重新启动已决定暂缓的问题。
3. 预查潜在冲突及影响，准备可审阅的合并范围与验证结论。若冲突处理会改变已验收行为或超出已批准范围，先说明影响并请求明确批准。
4. 获得用户对合并到内部 main 的明确批准后，才可执行 Merge。未验收功能不得擅自并入 main。

**合并后的检查**：记录实际合并结果和 main Commit，确认工作区状态，并按冲突或集成影响完成必要验证。合并不是 Push、公开源码同步或部署。发生失败或版本偏差时，不自动推进后续发布动作。

### 03｜正式版本准备发布

**冻结来源**

- 从内部 main 的已验收版本选定一个明确的 Git Commit，记录完整 Commit ID 和准备发布的版本号。冻结依据是具体 Commit，不能只记录可能移动的分支名。
- 从该 Commit 对应的干净源码生成正式构建及干净公开源码。遵守固定工具版本、冻结依赖安装、补丁、定义完整性和资源校验要求。
- 正式网站构建使用已授权资源模式；公开构建使用既有合法回退方案。两种模式共享同一应用源码，记录模式和资源完整性信息，不能因字体资源不同另行开发业务代码。
- 默认 clean 导出用于发布。使用 --allow-dirty 的准备快照仅用于准备验证，不能成为冻结版本对应源码或正式发布依据。
- 不使用旧 dist 代替冻结 Commit 的构建验证；不混合不同版本的源码、设备定义、资源或构建文件。任何发布范围变化都必须重新明确来源和对应验证，不能悄悄替换冻结内容。

**发布对应记录至少包含**

| 记录项 | 必须明确的内容 |
| --- | --- |
| 内部版本 | 版本号、内部 main 完整 Commit ID、验收范围与已知限制 |
| 构建输入 | Node/Bun 版本、锁文件与补丁标识、资源模式及必要资源哈希 |
| 公开源码 | 导出来源 Commit、SOURCE_SNAPSHOT.json、SOURCE-FILES.json、源码指纹和文件核查结果 |
| 正式产物 | 构建来源、产物文件清单及哈希、构建和定义完整性验证结果 |
| 后续关联 | 公开仓库对应 Commit/源码获取位置、部署标识和核查结果（在对应步骤实际完成后记录） |

**进入下一阶段的条件**：源码和产物均能追溯至同一个冻结 Commit，必要验证有实际结果，资源使用和公开范围明确。不得填写尚未执行的公开 Commit、Push 或部署结果。

### 04｜GitHub 公开源码仓库

**同步与核查**

- 使用现有公开源码导出流程，从冻结来源生成公开源码，再更新独立的 morgrie-configurator-public。源目录与公开镜像之间逐文件核对相对路径和哈希，保留结构和必要许可、构建及来源文件。
- 仅同步经过审核的公开 source 内容，不复制其父目录中的私有字体、validation、内部报告或其他准备文件。不复制内部仓库的完整 .git 历史；必要上游归属和来源 Commit 标识不等于复制内部开发历史。
- 不上传未经授权的字体二进制、私有文件、凭据或敏感资料。合法上游版权与许可证声明须保留。
- 检查公开文档及规则引用是否完整可读。若现有导出清单未包含新增的规则文档，应先报告并安排必要的导出规则维护，不能带着失效引用发布，也不能靠单独修改公开副本掩盖来源差异。
- 公开镜像与准备发布版本对应，不直接 Merge 内部 feature/main 分支，不在镜像中独立开发相同功能。需要修复时返回内部开发流程，再从批准版本重新导出。

**Git 与上传边界**

- 公开仓库使用独立 Commit 更新；执行该 Commit 前须有用户明确批准，记录它与内部冻结 Commit 的对应关系。
- Push 必须另有明确批准，核对公开仓库、分支、待推送内容和对应版本。对本地复制、内部 Commit 或公开 Commit 的批准不自动允许 Push。
- 创建远程仓库或初始化独立本地仓库必须在用户当前任务授权范围内，不能把本流程当作预先授权。
- Push 后核对已发布的源码 Commit、文件及可获取位置，确保按现有许可证要求提供对应源码；本地目录存在不等于源码已经公开可获取。

**进入正式部署的条件**：准备上线版本的对应源码已按许可证要求提供，公开 Commit 与内部冻结 Commit 的对应关系有证据，且不存在长期版本脱节。

### 05｜Cloudflare 正式部署

**部署前**

1. 再次确认版本号、内部冻结 Commit、对应正式产物、资源模式、公开源码位置及核查结果。
2. 确认 Cloudflare 使用的是该 Commit 对应产物，不使用其他目录、旧构建或浮动来源替代。
3. 必须获得用户明确的正式部署批准。Commit、Merge、源码同步和 Push 都不自动包含部署权限。
4. 现有 workflow 或自动触发器不能替代批准。若某次 Push 或其他操作会触发正式部署，执行前必须同时具备该操作及部署的明确授权；缺少任一授权就不得触发该正式部署链路。本规则不在文档更新时自动改动流水线配置。

**部署后**

- 检查实际部署版本与批准的内部 Commit/产物一致，记录部署标识。
- 检查 HTML、关键静态资源、Favicon、字体资源模式、设备定义及必要运行功能，区分 HTTP/软件检查与真实设备结果。
- 按 TESTING_RULES.md 保持设备安全边界：运行检查不自动授予改键、宏、灯光、布局或导入写入权限，不执行未批准的恢复默认或刷写。
- 对异常先记录和报告，按已批准的应对范围处理；没有覆盖的重发、版本替换或回退需另获明确批准，不把一次部署批准扩大为任意后续部署。

**完成条件**：正式站点、发布记录和公开对应源码指向同一批准版本，部署后检查及未通过事项如实记录。不能因为用户暂缓修复就把问题标为已解决。

## 操作分离与明确批准

| 动作 | 含义 | 不能据此推定获准的动作 |
| --- | --- | --- |
| Commit | 在指定仓库记录已审阅变更 | Merge、Push、部署 |
| Merge | 将已批准范围合入指定目标分支 | Push、公开源码同步、部署 |
| 公开源码同步 | 从指定冻结来源导出、核查和更新本地镜像 | Commit、创建远程仓库、Push、部署 |
| Push | 将批准的公开/内部提交发送到指定远程与分支 | 未明确批准的正式部署 |
| Cloudflare 正式部署 | 发布批准版本的对应产物 | 未约定的改版、重发、回退或设备配置写入 |

明确批准应能辨明动作、仓库/目标分支、版本或变更范围。用户可以一次明确批准多个具体动作，但不得把含糊的“准备发布”或对某一步的批准扩展到其他步骤。已有授权在约定范围内继续有效，不反复请求同一批准；目标或范围变化时重新说明并确认。获得批准前，先把已授权的分析、准备、验证与可审阅结果完成。

## 禁止事项与例外

1. 禁止跳过五阶段中必要的审核与验收环节。
2. 禁止未经用户明确批准执行 Commit、Merge、Push 或正式部署。
3. 禁止将提交、合并、公开源码同步和 Cloudflare 部署混为同一操作。
4. 禁止内部仓库和公开仓库独立开发相同功能。
5. 禁止公开源码与正式部署版本长期不对应；上线前必须具备对应源码提供条件。
6. 需要例外时，先说明原因、涉及阶段、影响、风险及替代验证方式，获得用户明确批准后才可在该范围内执行。不能先执行再把结果当作批准，也不能因历史上有过例外就默认本次同样适用。

本流程不覆盖或削弱 TESTING_RULES.md、现有设备安全、许可证及其他开发要求。仅修改规则文档不构成任何实际 Git 提交、合并、Push 或部署授权。
